# ctx-handoff 北極星

> Maintainer document in Traditional Chinese: what each feature is for and how we tell whether it works. Users: start with [`README.md`](../README.md).

這份文件定義 ctx-handoff 要達成什麼，以及每個功能怎樣才算「成功」。改程式、排優化順序、判斷要不要加功能，都先對照這裡。實作與平台細節在 [`CLAUDE.md`](../CLAUDE.md)。

- 狀態：2026-10-09 起草。目前階段**不擴張功能，只優化既有功能**。
- 文中的「建議目標」是起草時提出的數字，維護者確認前不算定案；「待決定」的項目列在最後。

## 北極星

**長時間用 Claude Code 做事時，不因為對話本身的限制而掉進度、白花錢、或重講同樣的事。**

「對話本身的限制」指三件事：context 越來越長、快取一小時就過期、對話被清掉（交接、`/clear`、當機、另開新對話）。

整體成功的樣子：一段工作從開始到結束，使用者不需要

1. 自己留意 context 大小或決定何時換對話；
2. 換對話後重新解釋做到哪；
3. 離開一陣子回來時，為整段對話重新付全價；
4. 把同一句糾正講第二次。

## 怎麼用這份文件

- **改動先說它服務哪個支柱、改善哪個指標。** 說不出來的改動不做。
- **先量再改。** 指標還量不到的功能，優化的第一步是補量測，不是改行為。
- **護欄不能變差。** 每個功能列了「不能變差的事」，改善指標時要一起檢查。
- **用結果判斷，不用寫死的上限控制輸出**（維護者 2026-10-09 決定）：模型該寫多少由內容決定，好不好看結果指標（接續率、補背景次數等）。數字上限只留給防止失控的保險（例如交接最多等 3 分鐘），不拿來調品質，免得每次都要回頭改數字。
- **新功能**（暫停擴張期間之後）要先放得進某個支柱，並寫出成功定義，才進實作。

## 支柱與功能

| 支柱 | 目的 | 功能 |
|---|---|---|
| A 接得上 | 換對話後不掉進度 | 自動交接、離席交接、進度備忘 |
| B 不白花錢 | 不為等待與過長的 context 付錢 | 保持快取（加上 A 的交接、C 的整理用便宜模型） |
| C 不用重講 | 糾正過的事跨對話記得 | 專案筆記（整理＋帶入新對話）、放進專案 |
| D 不重複犯錯 | AI 的壞習慣當下攔住 | 守門、重複失敗提醒、沒驗證擋下、回覆語言提醒 |
| E 控制面 | 人只在需要判斷時介入 | 面板、設定、`/handoff` 狀態與指令 |

**A、B、C 是主線**，三者共用同一條流程：回合結束排閒置計時 → 停下時判斷門檻 → 先整理再 `/clear` → 新對話帶入。**D 是支線**：只管當下這一回合，壞了不影響主線，評估時和主線分開。這個 mod 之後會繼續收進相關功能（維護者決定），所以支線留在這裡，但不能拖累主線。

## 各功能的成功定義

每個功能寫四件事：**目的**、**成功的樣子**（使用者感受得到的）、**指標**（怎麼量、從哪裡量、建議目標）、**護欄**（改動時不能變差的）。「量得到」欄：✅ 現在的資料就能算；◐ 要人工抽查或另寫工具讀現有資料；❌ 現在沒有紀錄，要先補。

### A1 自動交接

- **目的**：context 長了之後，每回合的成本與回答品質都會變差；交接讓它們一直維持在短對話的水準，使用者不用管 context。**省錢與品質兩個都要**（維護者 2026-10-09 決定）：交接後成本一定要下降；摘要的資訊量也要足夠，新對話不能因為摘要太薄而重問、重查或做錯。
- **成功的樣子**：到門檻時自動換到新對話，新對話第一個回應就接著原本的工作，不問「我們在做什麼」，使用者也不用補背景；交接期間打的字一個都不掉。
- **已知問題**：有使用者反映交接內容資訊量偏少。現有 18 份存檔（context 36k–714k）的摘要都只有 1,000–3,300 字、輸出 1,200–2,500 tokens，長度和 context 大小幾乎無關：600k 以上的對話也只留約 2,600 字。原因之一是提示寫死「全文不超過 1800 字」。依上面「用結果判斷」的原則，這個字數上限要拿掉，改由提示說明接手者需要什麼、讓內容決定長度（優化階段處理）。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 交接完成率 | 觸發的交接中，新對話真的收到摘要的比例 | `stats:` 的 `handoff.<種類>.ok`／`.fail` | ≥ 95% | ✅ |
| 接續率 | 交接後新對話第一個回應直接接續工作，沒有反問或重做已完成的事 | 對話檔抽查 | 抽查 10 次 ≥ 9 次 | ◐ |
| 補背景次數 | 交接後前 3 則使用者訊息裡，在補充 AI 不知道的背景或糾正它弄錯的狀態的次數 | 對話檔抽查 | 平均 < 0.5 次 | ◐ |
| 重查次數 | 交接後新對話為了弄清楚舊對話已知的狀態而重讀檔案、重跑指令的次數 | 對話檔抽查 | 先量，再訂 | ◐ |
| 訊息不掉 | 交接期間攔下的訊息全部送進新對話 | `stats:` 的 `held`、`held.lost` | 100% | ✅ |
| 中斷時間 | 觸發到新對話開始的秒數 | `handoffs:` 的 `usage.ms` | 只記錄觀察，不設目標（現在 11–30 秒；最多等 3 分鐘的保險不變） | ✅ |
| 交接後成本 | 交接後每回合平均輸入成本，對照交接前最後幾回合 | 對話檔每回合 usage | 明顯下降（數字待量後訂） | ◐ |

- **護欄**：背景工作、排程、子代理還在跑時不切斷（延後機制）；失敗後不在短時間內反覆重試；交接中 `/clear` 失敗時留在舊對話、不丟訊息。

### A2 離席交接

- **目的**：快取一定會過期時，先備好一份摘要；使用者回來可以從摘要重新開始，不必用全價重寫整段對話。
- **成功的樣子**：離開很久回來，看到可以換新對話的提示；選 `resume` 後，新對話的花費遠低於舊對話整段重寫快取。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 使用率 | 產生的離席交接中，使用者選 `resume`／`continue`／被過時刪除的比例 | `stats:` 的 `away.resume`／`away.continue`／`away.stale` 對 `handoff.away.ok` | 先量，再訂 | ✅ |
| 回來的花費 | `resume` 後第一則的快取寫入量，對照舊對話整段大小 | 對話檔 usage | ≤ 舊對話的 10% | ◐ |

- **護欄**：使用者回來後送出的第一則訊息不能遺失；選擇留在舊對話時照原樣送出。

### A3 進度備忘

- **目的**：自動交接沒涵蓋的情況也接得上：使用者自己 `/clear`、程式當掉、另開新對話。
- **成功的樣子**：新對話一開始就知道上一段停在哪、下一步是什麼，使用者不用重講。使用者自己開新對話時多半是要接著做原本的事；要做別的事會自己說，所以不需要「不該接的時候不提供」的判斷（維護者 2026-10-09 確認）。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 接續率 | 帶入進度的新對話，第一個回應有接上（提到或延續上一段任務） | 對話檔抽查 | 抽查 10 次 ≥ 8 次 | ◐ |
| 新鮮度 | 提供時進度備忘距離最後一次整理的時間 | `progress:` 的 `at` | 大部分 < 1 小時 | ✅ |
| 不重複 | 交接過的對話不再收到同一段的進度備忘 | `progress:` 的 `handed`、`offered` | 0 次重複 | ✅ |

- **護欄**：不佔經驗檔、不常駐 context；整理沒有新進展時保留上一份。
- **已知限制**：進度只跟著整理的時機更新，短對話或當機前可能沒有或落後。新對話是否真的會用到這份備忘，還沒有實機驗證。

### B1 保持快取

- **目的**：離開不到 3 小時回來，第一則訊息還是從快取讀，不用全價重送。
- **成功的樣子**：短暫離開再回來，回應速度與花費和沒離開一樣。離開 1–3 小時再回來接著做是常見情況（維護者 2026-10-09 確認），所以刷新預設划算；回來命中率仍要量，用來確認。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 回來命中率 | 刷新過的閒置中，使用者在快取還有效時回來的比例 | 沒有統計 | 先量，再訂 | ❌ |
| 淨省下的錢 | 回來時免去的快取重寫費用，減去所有刷新請求的費用 | 對話檔 usage、刷新紀錄 | > 0 | ◐ |
| 刷新有效 | 刷新後回來第一則的 `cache_creation` 接近 0 | 對話檔 usage | 接近 0 | ✅ 實機已證實 |

- **護欄**：使用者不回來時，花在刷新的錢有上限（`max_refresh` 次）；刷新不改主對話內容。

### C1 專案筆記（整理＋帶入新對話）

- **目的**：使用者的偏好與糾正跨對話保留，新對話一開始就照做。
- **成功的樣子**：同一句糾正不會出現第二次；記下來的內容是對的，人很少需要去刪。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 再犯率 | 已經帶入新對話的規則，之後又因同一件事被使用者糾正的次數 | 經驗檔次數與根據 | 趨近 0 | ❌ 次數混了「再糾正」與「做法被證明有效」，要分開記 |
| 記錯率 | 新增的條目中，之後被人在面板刪掉的比例 | `.ctx-handoff-backup/` 只有備份，沒有計數 | ≤ 10% | ❌ |
| 整理成功率 | 整理請求中成功寫入或確認沒變動的比例 | `stats:` 的 `distill.ok`／`distill.fail` | ≥ 95% | ✅ |
| 每次整理花費 | 每次整理的輸入與輸出 tokens | `distill:last:` 的 usage | 先量，再訂上限 | ✅ |
| 帶入大小 | 新對話開頭帶入的經驗字數 | 經驗檔＋帶入規則可算 | 上限待定 | ◐ |

- **護欄**：只有使用者自己說過的話才能記成偏好（引用比對）；整理不因條數多而刪；不寫內建 auto memory 的 `MEMORY.md`。
- **現況與方向**（維護者 2026-10-09）：使用者感覺不出有沒有用，也看不出記錯多少，所以只能靠量測。優化重點是**整理的提示詞**：讓該記的都記到、記的內容正確、寫法讓新對話照得做。
- **怎麼判斷提示詞改得好不好**：拿幾段真實對話當固定題庫，同一段對話分別用舊提示與新提示跑整理，比較三件事：
  1. 漏記：使用者在對話裡明確糾正或表達偏好的地方，有沒有記到；
  2. 記錯：記下的條目和原話對不對得上、有沒有把助理的做法當成使用者要求；
  3. 被程式擋掉的比例：輸出格式或引用不合格而被丟掉的條數（`distill:last:` 已有 `rejected`）。

  新提示在題庫上漏記少、記錯不增加，才換上去。

### C2 放進專案

- **目的**：證實過的規則與流程畢業成 repo 的正式文件或 skill。好處有兩個：不用這個 mod 的人和工具也能受益；這些規則移出每次帶入的 context。
- **成功的樣子**：經驗檔不會無限變大；重要的做法最後都在 repo 裡找得到。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 畢業率 | 達 3 次的規則與流程，在交代上限內被標成「已在」或「不放」的比例 | `promote:`、經驗檔的「專案：」 | ≥ 80% | ✅ |
| 帶入縮減 | 畢業後帶入大小的變化 | 同 C1 帶入大小 | 下降 | ◐ |

- **護欄**：mod 自己不寫 repo、不 commit；同一條不在短時間內交給多個對話。
- **實際檢查**（2026-10-09，依本機經驗檔、store 與目標 repo）：
  - 專案 A：5 條達 3 次的規則都標成「已在」該 repo 的 AI 施工文件，到 repo 核對都找得到對應內容（2026-10-07 commit）。**規則畢業成功。**
  - 同一個 repo 的 3 條啟用中守門已交代滿 2 次，卻都沒有回報、仍是啟用狀態，之後也不會再交代。**守門畢業失敗，而且卡住。**
  - 專案 B（是 git repo）：5 條達 3 次的規則還沒交代過；這個功能 2026-10-07 才上線，之後那裡沒有新對話帶入過經驗，推測只是還沒輪到，未確認。
  - ctx-handoff 本身的經驗檔沒有任何規則，無從畢業，不能當例子。
- **重新設計**（維護者 2026-10-09 決定，原則：使用者什麼都不用做，系統自己確認）：
  - 卡住的原因：整條流程靠 AI 記得「放進 repo」和「呼叫回報工具」兩件事；忘了回報，mod 就以為沒放，交代 2 次後永遠停住，也沒人知道。把卡住的項目丟給使用者處理是讓人替 AI 收尾，方向不對。
  - **確認改由背景整理做**：整理本來就讀這段對話。看到 AI 改了 repo 的檔案（CLAUDE.md、skill、hook）、或在回覆說「已經在 X」，就記成「已在 X」，程式確認那個檔案真的存在；看到使用者說不要，就記成「不放」（要附使用者原話）。拿掉回報工具 `mark_in_project`（之前「工具被撤掉、AI 直接改 store」的事故就出在它）。
  - **交代的時機看事件，不看時間**：交代給一段對話後，那段對話還在進行時不交給別的對話（避免兩邊重複放）；那段對話結束（`session.end`），或背景整理已看過交代之後的內容卻沒看到放好，下一段新對話再交代。沒有小時數或次數上限（原本的 6 小時與 2 次是實作時隨手定的，沒有依據）。
  - 使用者要做的事：沒有。面板看得到每條放在哪。
  - 代價：要等下一次整理才記上；整理能不能認出「放好了」要靠提示詞，放進之後的 evaluation。
  - 未實測：程序被直接關掉時 `session.end` 是否觸發；不觸發時靠「整理看過卻沒放好」補上。
- **成功要多看一件事**：交代過卻一直沒記上的項目數，應趨近 0。

### D1 守門

- **目的**：文字規則 AI 還是會違反時，用程式強制攔下。
- **成功的樣子**：擋到該擋的，從不誤擋。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 命中 | 啟用後的命中次數 | `guards:` 的 `hits` | > 0（否則不必啟用） | ✅ |
| 誤擋 | 命中中不該擋的比例 | `stats:` 的 `hits`（最近 20 筆指令片段），人工或評估判斷 | 0 | ◐ |
| 再犯 | 啟用後同一條規則又被使用者糾正的次數 | 同 C1 再犯率 | 0 | ❌ |

- **護欄**：只有使用者核准的才生效；hook 自己出錯時一律放行。
- **角色**：規則變成 repo 正式做法之前的試行區。現行設計就是這樣：守門放進專案後，mod 這邊的守門會停用。
- **成功再加一條**：提醒文字不能過時。repo 的做法改了，守門的提醒要跟著改或停用。
- **實際檢查**（2026-10-09，專案 A 的 4 條守門，都是 remind）：
  - 第 3 條「推送前檢查」命中 10 次，已放進專案並停用，走完了試行到畢業的整個流程。但它的提醒還寫著「先跑 preflight 再 push」，repo 後來改成不要這樣做；如果還在啟用中，就是在提醒錯的事。
  - 其他 3 條啟用約 3 天：命中 0、1、0 次。看不出是 AI 本來就照做，還是 regex 沒對到。
  - 只有「命中次數」，沒有記錄每次命中是否正確，所以誤擋量不出來。

### D2 重複失敗提醒

- **目的**：同一個工具因同樣原因連續失敗時，讓模型停下來找原因，不原樣重試。
- **成功的樣子**：提醒之後，這段連續失敗很快結束。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 收斂 | 提醒後，同工具同原因再失敗的次數 | 對話檔（提醒附在工具結果 `context`） | ≤ 1 | ◐ |
| 誤報 | 提醒後原樣重試就成功的次數（代表是暫時性錯誤，例如頁面還在載入、逾時，原樣重試本來就對） | 對話檔 | 0 | ◐ |

- **護欄**：不擋任何呼叫；使用者中斷或拒絕的不算失敗。
- **實際檢查**（2026-10-09，掃所有工作區的對話檔，提醒記在 `hook_additional_context` 列）：上線以來只觸發 2 次。
  - 瀏覽器自動化工具：提醒後換了做法，下一次就成功。符合預期。
  - 截圖工具：提醒後**原樣重試就成功**。錯誤是暫時性的，這次提醒其實是誤報。
  - 次數太少，還不能下結論；但暫時性錯誤（逾時、載入中）應該排除在提醒之外，或提醒文字要允許「確認是暫時性錯誤就重試」。

### D3 沒驗證擋下

- **目的**：模型說完成、改過程式卻沒跑任何測試時，擋下停止一次，讓它補驗證。
- **成功的樣子**：說「完成」時真的驗證過；不該擋的時候不擋。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 補驗證率 | 擋下後模型真的跑了測試或檢查的比例 | 對話檔 | ≥ 90% | ◐ |
| 誤擋 | 已驗證或沒改程式卻被擋的次數 | 對話檔抽查 | 0 | ◐ |

- **護欄**：每回合最多擋一次；子代理與其他 Stop hook 已擋下的不處理。
- **已知代價**：擋下時畫面一定會跳「Stop hook error occurred」，無法改。
- **實際檢查**（2026-10-09，掃所有工作區的對話檔）：上線以來真正擋下只有 1 次，而且是**誤擋**。當時已經跑過 `tools/check.mjs` 和 land，被擋是因為子代理改檔被算進主對話；這個誤判之後已修（只記主對話自己的呼叫）。修好後沒有再觸發過，所以「擋得對不對、擋了有沒有用」都還沒有資料。

### D4 回覆語言提醒

- **目的**：長對話裡模型的說明漂成別的語言時，提醒它回到使用者的語言。
- **成功的樣子**：說明一直是使用者的語言；使用者要求別種語言的內容時不會被打擾太多。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 回正率 | 提醒後下一段說明回到目標語言的比例 | 對話檔 | ≥ 90% | ◐ |
| 誤報 | 使用者本來就要別種語言（翻譯、英文文件）卻被提醒的次數 | 對話檔抽查 | 很少，數字待量 | ◐ |

- **護欄**：不改請求（不動 model、effort，不影響快取）；分不出繁簡時不提醒。
| 復發 | 提醒後又漂回去、需要再提醒的次數 | 對話檔 | 越少越好，先量 | ◐ |

- **實際檢查**（2026-10-09，掃所有工作區的對話檔）：觸發 17 次，3 個工作區，其中 15 次在專案 A 同一段很長的對話。
  - **觸發都正確**：每次提醒前那段說明都是整段英文（漢字 0），使用者在用中文。
  - **提醒後馬上回正 13 次（76%）**，兩段說明內回正 16 次；有 1 次連續兩段都還是英文。
  - **效果短暫**：同一段長對話裡反覆漂回英文、反覆被提醒，提醒治標不治本。
  - 提醒文字附在工具結果或下一則訊息後模型確實看得到，這點已由上面的回正證實。

### E 面板、設定與指令

- **目的**：平常全自動；人只在需要判斷時介入（刪記錯的內容、核准守門、調設定）。
- **成功的樣子**：使用者不需要手改經驗檔或 store 檔；按下去立刻有反應；改設定下一則訊息就生效。

| 指標 | 定義 | 資料來源 | 建議目標 | 量得到 |
|---|---|---|---|---|
| 手改次數 | 使用者為了修正 mod 的資料而手動編輯檔案的次數 | 對話紀錄抽查 | 0 | ◐ |
| 狀態可查 | 背景失敗都能在 `/handoff` 看到原因 | 程式行為 | 每種失敗都有 | ✅ |

- **護欄**：面板不放狀態數字（交給 status line）；刪除要按兩次並先備份。
- **實際檢查**（2026-10-09）：對話檔裡 `/handoff panel` 開過 15 次；三個工作區的備份資料夾共有 5 份刪除前備份（2026-10-05 到 10-06，含 `tools/notes.mjs` 的備份，分不出哪些是面板刪的）；面板設定目前只存了 `threshold`。看不出使用者有沒有手改過檔案。這一項沒有發現明確問題。

## 跨功能的耦合點

讀程式看到的地方，優化時先看。都還沒實測；第 2 點是推論。

1. **Stop 一個 hook 做兩件事。** 「沒驗證」擋下的那次停止不判斷交接，要等下一次停下；到門檻又剛好說完成時，交接會晚一輪。
2. **整理的鎖會讓交接前整理靜默跳過。** 交接開始時若「每 N 則」的整理正在跑，交接前那次直接跳過。正在跑的那次會排入差異，差異記在舊 session id 底下，`/clear` 後換了 id 就不會帶給新對話（經驗檔仍有寫入）。
3. **`prompt.submit` 擠了 6 件事。** 重讀設定、交接中攔訊息、離席攔訊息、重置計時與改檔紀錄、記錨點、帶入差異與語言提醒。改其中一件要讀懂全部的先後。
4. **開關有兩套存法。** `refresh`、`distill` 是 store 的獨立鍵，其他設定在 `settings` 物件裡，面板要特別處理。
5. **store 是所有 session 共用的一個 JSON 檔。** 每則訊息都寫 `last:`，守門命中寫整份守門清單，面板改值寫 `settings`。多個 session 同時開時的頻率與覆寫風險沒量過。
6. **碰 `$` 的程式都在 `hooks/register.ts`。** 平台限制，拆檔只能搬純邏輯，新功能幾乎都會再長在這個檔案。

## 非提示詞問題的處理紀錄

提示詞的品質之後用 evaluation 處理；先把流程與機制的問題逐項解決（2026-10-09 起）。

| # | 問題 | 結論 |
|---|---|---|
| 1 | 交接撞上正在跑的整理，交接前整理被跳過，最後一段沒整理 | 已修（c7635fb）：交接先讀好片段再 `/clear`，等正在跑的整理結束接著整理；交接不再等整理 5 秒。順帶修好交接後新對話可能拿到過時進度備忘 |
| 2 | 「沒驗證」擋下的那次停止不判斷交接 | 不改：擋下代表回合沒結束，這時交接會切斷驗證；驗證完第二次停下就會判斷交接，代價只是晚一輪 |
| 3 | 守門放進專案卡住、看不到 | 已實作（58b5f51，見 C2）：背景整理確認、交代時機看事件、拿掉回報工具 |
| 4 | 守門提醒過時 | 不另做機制：守門只是放進 repo 前的試行區，#3 修好後在 git repo 開新對話就交代、背景整理確認放好就停用，試行期從「可能一直卡著」縮短到下一段新對話；之後以 repo 為準 |
| 5 | 重複失敗提醒對暫時性錯誤誤報 | 已改提醒文字：看起來是暫時性錯誤（逾時、還在載入、連線中斷）就稍等再試一次，判斷交給看得到完整錯誤的模型；不在程式維護關鍵字清單。資料只有 2 次，等評估機制再看效果 |
| 6 | 缺紀錄（失敗只留最後一筆、離席選擇、次數兩種意思、守門命中對錯、攔下訊息送達） | 已補記帳：`stats:<工作區>` 累計交接與整理的成功／失敗、離席選擇、攔下與遺失的訊息、守門命中（留指令片段供評估判斷對錯），`tools/status.mjs` 顯示。「次數兩種意思」要改提示詞與經驗檔格式，移到提示詞階段 |
| 7 | 程式結構（`prompt.submit` 做 6 件事、開關兩套存法） | 先不做：查過不影響品質（hook 出錯時引擎跳過它、訊息照常送出；6 件事各有測試），只是好不好讀。之後要改那段時順手整理 |
| 8 | 共用存檔的覆寫風險 | 已實測（見 CLAUDE.md 平台事實）：不同的鍵不會互蓋，同一個鍵的讀改寫會。同工作區多個 session 共用的鍵（守門、交代紀錄、統計、`seen`、面板設定、handoff 清單）在兩邊幾毫秒內同時寫才會少一筆；最嚴重是面板核准守門剛好撞上另一個 session 的守門命中計數，核准會不見（面板看得到，再按一次） |
